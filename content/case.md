title: Example Retail
---

Example Retail 是整門課共用的虛構企業。每個模組都接續前一個模組的進度，最後在 Capstone 整合成一份完整的設計包。公司、人物與系統都是虛構的。

## 公司概況

| 項目 | 設定 |
|---|---|
| 產業 | 連鎖零售（生活用品），全台 120 家門市 |
| 通路 | 門市、電商網站、App |
| 會員 | 約 80 萬人；門市與電商的會員資料各自獨立 |
| 既有系統 | 地端 POS（自建，使用十年以上）、套裝 ERP、外包廠商維運的電商平台、用試算表管理的促銷活動 |
| IT 團隊 | 8 人，多數熟悉地端系統；已開始用 AI coding agent 開發 |
| 雲端 | 剛決定導入 AWS，還沒有帳號治理 |

## 要解決的問題

Example Retail 想推出**全通路會員平台**：整合門市與電商的會員和訂單，提供點數、優惠券與門市取貨。

限制條件：

- 預算有限。
- 必須符合個資法。
- 週年慶流量約為平日的 10 倍。
- POS 不能停機。

## 利害關係人

| 角色 | 在意的事 |
|---|---|
| 營運長 | 出資方，在意投資報酬與上線時程 |
| 門市營運部 | 門市作業不能變慢、POS 不能停 |
| 行銷部 | 點數、優惠券與會員活動能不能快速推出 |
| IT 主管 | 團隊能力、維運負擔與既有系統的整合 |
| 資安負責人 | 會員個資保護與存取控制 |
| 外包電商廠商 | 平台改動的範圍、時程與責任分界 |

## 各模組的案例進度

| 模組 | 案例進度 |
|---|---|
| 1 | 為全通路會員平台做需求探索與系統分析 |
| 2 | 畫出平台的 C4 圖，寫下第一批 ADR |
| 3 | 決定平台採用的架構風格，切出 bounded context |
| 4 | 串接 POS、ERP、電商平台與 AI 客服用的 LLM API |
| 5 | 設計會員與點數的資料模型，處理點數一致性 |
| 6 | 設計 AWS 帳號結構與部署架構 |
| 7 | 員工 SSO、會員個資保護、威脅建模 |
| 8 | 週年慶尖峰、SLO、災難復原與成本 |
| 9 | 用 coding agent 交付平台 |
| 10 | PoC → 10 家門市 pilot → 逐步遷移會員資料 |
| 11 | 向營運長提案 |
| 12 | 整合前面所有成果成為完整設計包，並處理新加入的需求：門市即時庫存查詢 |
