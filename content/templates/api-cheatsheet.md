# API 技術選擇速查表

| 技術 | 用途（一句話） | 什麼時候選 | 代價／要注意 | Example Retail 的例子 |
|---|---|---|---|---|
| API | 系統提供給其他程式的窗口與合約 | 不同團隊、不同公司或多種使用者要取得資料 | 要設計、寫文件、長期維護；合約不能隨便改 | 物流商查詢待出貨訂單 |
| 破壞性變更 | 會讓既有使用者壞掉的改動 | 盡量避免；先加後減，新舊並存 | 過渡期要同時維護新舊 | phone 改名 mobile |
| REST | 用網址、HTTP 方法、狀態碼表達 API | 對外 API、單純的資源操作，預設的起點 | 複雜畫面要多次請求；回應常有多餘欄位 | GET /orders/1001 |
| JSON | 人與程式都讀得懂的文字資料格式 | REST API 的預設格式 | 本身不驗證內容；日期與金額要另外約定 | 訂單的品項陣列 |
| GraphQL | 用戶端指定要哪些欄位 | 多種用戶端需求不同、一個畫面組合多種資料 | 伺服器要限制查詢成本；快取與權限較複雜 | App、網站、平板的首頁 |
| gRPC | 依共同的介面定義呼叫遠端功能 | 內部服務之間頻繁、低延遲的呼叫 | 內容不能直接閱讀；瀏覽器要額外處理 | 訂單服務呼叫庫存服務 |
| Polling | 定時詢問有沒有新消息 | 變動不頻繁，或晚一點知道沒關係 | 多數請求白問；間隔決定延遲 | 今日營業額每隔一段時間更新 |
| Webhook | 事情發生時，對方伺服器呼叫你的網址 | 伺服器對伺服器的事件通知 | 要驗證來源、處理重複與遺漏 | 物流商通知包裹已送達 |
| SSE | 伺服器對瀏覽器的單向持續推送 | 只需要伺服器往瀏覽器送更新 | 要維持大量開著的連線 | 商品頁的剩餘數量 |
| WebSocket | 雙向的長連線 | 雙方都要主動、頻繁地送訊息 | 最複雜；重連與驗證要自己處理 | 線上客服對話 |
| 錯誤格式 | 一致的錯誤代碼、訊息、追蹤編號 | 所有 API 都要 | 不可洩漏內部細節 | 點數不足的錯誤代碼 |
| 冪等鍵 | 讓重送的請求不會重複執行 | 扣款、下單、寄通知等不能重複的操作 | 伺服器要保存識別碼與結果 | 進電梯時重送的訂單 |
| 版本 | 讓新舊合約並存 | 必須做破壞性變更時 | 多個版本同時維護；要有退場計畫 | /v1/orders 與 /v2/orders |
| 限流 | 限制每個使用者的請求頻率 | 有外部使用者，或有昂貴的操作 | 額度要合理，並能為大客戶調整 | 每個廠商金鑰的每分鐘上限 |
