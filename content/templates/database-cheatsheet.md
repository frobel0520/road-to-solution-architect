# 資料庫技術選擇速查表

| 技術 | 用途（一句話） | 什麼時候選 | 代價／要注意 | Example Retail 的例子 |
|---|---|---|---|---|
| 關聯式資料庫＋SQL | 用嚴格表格與主外鍵保存資料，支援複雜查詢 | 會員、訂單、帳務等結構固定且重視正確性的資料 | 欄位調整要經過遷移；跨多機水平擴展較費工 | 會員資料表與訂單資料表 |
| 文件型 NoSQL | 用類似 JSON 的樹狀文件存資料 | 欄位經常變動、不同筆資料屬性差異大 | 跨文件關聯弱；應用程式要自己把關欄位格式 | 衣服、電鍋、清潔劑等屬性多變的商品目錄 |
| 鍵值型 NoSQL | 用一個 Key 極速讀寫對應的一包 Value | 只憑唯一編號存取、要求幾毫秒內回應 | 無法依內容做複雜條件篩選或排序 | 登入 Session 與暫存購物車 |
| 寬欄型 NoSQL | 針對海量寫入與橫向擴展設計的表格 | 每秒超高寫入量、時間序列與歷史事件紀錄 | 查詢條件必須事先設計好，不支援隨意 JOIN | 網站點擊流與門市設備紀錄 |
| 圖形型 NoSQL | 用節點與邊保存與查詢多層關係 | 需要追蹤三層以上關係的推薦或關聯分析 | 一般列表統計與大量掃描不如關聯式資料庫 | 「買 A 商品的人也買了什麼」推薦 |
| 資料庫索引 | 為指定欄位建立排好序的跳躍目錄 | 高頻查詢條件、關聯鍵變慢，避免全表掃描 | 佔用硬碟空間；每次寫入與更新都要順便維護 | 在會員表的手機號碼欄位建索引 |
| 交易與 ACID | 把多個讀寫綁成整體：全成功才提交，失敗就回滾 | 扣款、扣點數、限量庫存扣減等不可只做一半的操作 | 隔離越嚴格、鎖越多時併發吞吐量會下降 | 兌換點數時同時扣點數、扣庫存與建訂單 |
| 正規化 | 把資料拆成多張表，同一份事實只存一處 | 會員、商品主檔等需要避免改漏與不一致的資料 | 查詢時常需要跨表 JOIN | 訂單表只存會員編號，不重複存會員姓名電話 |
| 反正規化 | 為了讀取速度或歷史快照，刻意重複存欄位 | 需要保留當下快照，或避免高流量多表 JOIN | 佔空間；會變動的冗餘欄位必須確保同步更新 | 訂單明細直接存下單當下的商品名稱與成交價 |
| ORM | 把程式物件自動翻譯成 SQL 操作資料表 | 日常增刪改查、加速開發與統一存取寫法 | 容易寫出 N+1 查詢；複雜報表效能不如手寫 SQL | 用預先載入一次撈出 20 筆訂單與品名 |
