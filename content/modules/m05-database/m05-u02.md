## 情境

Example Retail 已經用關聯式資料庫管好會員與訂單了，但團隊很快遇到幾種「硬塞進表格很痛苦」的資料：商品規格五花八門，衣服有尺寸、家電有瓦數；週年慶時每秒上萬人打開購物車，只需要用一個編號極快讀出一包資料；或是想分析「買過這款保溫瓶的顧客，通常還買了什麼」，用 SQL 寫多層關聯查詢慢到跑不動。

這時候，工程師常會提起 **NoSQL（Not Only SQL，非關聯式資料庫）**。但「NoSQL」不是某一種資料庫，而是四種完全不同設計思路的總稱。

## 觀念

### 為什麼會出現 NoSQL

關聯式資料庫在資料結構固定、重視嚴格正確性時非常強大，但它要求「先定好表格才能放資料」，而且資料量暴增到單台機器裝不下時，跨多台主機做 `JOIN` 會變得非常慢。NoSQL 選擇放寬表格限制或放棄跨表關聯，換取**彈性結構**、**超高讀寫速度**或**更容易水平擴展到多台主機**。

比喻：關聯式資料庫像嚴格分類的檔案櫃，每份文件都要填同一張制式表格才能放進去；NoSQL 則像四種不同的收納工具——有的像活頁夾，有的像編號置物櫃，有的像流水帳捲軸，有的像犯罪電影裡的關係白板。比喻的極限是：現實中你可以把所有東西都塞進置物櫃，但在資料庫選型上，選錯收納工具會讓查詢變得極慢甚至寫不出來。

### NoSQL 的四種類型

1. **文件型（Document）**：把一筆資料存成一份類似 JSON 的樹狀文件，每份文件可以有自己的欄位。適合商品目錄（不同品類屬性不同）、文章內容、表單紀錄。缺點是跨文件關聯查詢不如關聯式資料庫方便。
2. **鍵值型（Key-Value）**：最單純的字典結構，只有「一個鍵（Key）」對應「一個值（Value）」。你只能憑鍵去拿值，不能問「幫我找值裡面價格小於 500 的」。速度極快，常用於登入 Session、快取、購物車暫存。
3. **寬欄型（Wide-Column）**：外觀看起來也有列與欄，但同一張表裡每一列可以擁有不同的欄位，而且資料是針對「海量寫入」與「橫向切分到數十台主機」設計的。適合網站點擊事件流、門市設備感測器紀錄、大量歷史訊息。
4. **圖形型（Graph）**：專門把資料存成「節點（例如會員、商品）」與「邊（例如購買、推薦、追蹤關係）」。當問題需要追三層以上的關係（例如「A 的朋友買過、但 A 還沒買過的商品」）時，圖形資料庫比關聯式資料庫的多次 `JOIN` 快非常多。

### 不要為了流行而放棄關聯式資料庫

NoSQL 並不是來取代關聯式資料庫的。多數系統的核心帳務、會員與訂單依然留在關聯式資料庫，只在特定痛點（例如商品規格、Session、海量日誌、推薦關係）搭配對應的 NoSQL 使用。

四種 NoSQL 各自為不同形狀的資料而生：先看「資料長什麼樣子」與「最常怎麼查它」，再決定要不要離開關聯式資料庫。

## 取捨

四種 NoSQL 類型與關聯式資料庫的比較：

| 類型 | 適合的情況 | 代價 |
|---|---|---|
| 文件型（Document） | 欄位經常變動、巢狀結構、多數時候整份讀寫的資料（商品規格、內容） | 跨多份文件的複雜關聯查詢較弱；欄位自由也代表應用程式要自己把關格式 |
| 鍵值型（Key-Value） | 已知唯一鍵的極速讀寫（Session、快取、購物車） | 無法依內容做複雜條件搜尋或排序 |
| 寬欄型（Wide-Column） | 超高寫入量、海量時間序列或事件紀錄（點擊流、設備紀錄） | 查詢模式必須事先設計好；不支援隨意換條件查詢與跨表 JOIN |
| 圖形型（Graph） | 多層關係追蹤（推薦系統、社交網路、詐欺關聯偵測） | 單純的列表統計與大量批次掃描不如關聯式資料庫 |

## 決策題

## 交給 AI 時要注意

- 不要只說「幫我選一個 NoSQL 資料庫」，要說清楚「資料長什麼樣子」「最常依什麼條件查詢」「每秒讀寫大概多少」。
- 若選擇文件型資料庫，請 AI 一起寫出欄位驗證規則，避免不同版本的程式寫進格式不一致的文件。
- 確認需要強一致性與跨筆交易的資料（例如扣款與扣庫存）是否仍應留在關聯式資料庫。

## 重點回顧

- NoSQL 不是單一技術，而是文件型、鍵值型、寬欄型、圖形型四種不同資料庫的統稱。
- 文件型適合欄位多變的樹狀資料；鍵值型適合只憑 ID 極速存取；寬欄型適合海量寫入與時間序列；圖形型適合多層關係查詢。
- 多數系統以關聯式資料庫為主力，只在特定場景搭配 NoSQL，而不是全面取代。
