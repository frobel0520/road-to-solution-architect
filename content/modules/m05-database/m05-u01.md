## 情境

Example Retail 有 80 萬名會員、上萬種商品與每天不斷湧入的訂單。如果資料只是隨便存成一堆文字檔或試算表，很快就會遇到三個問題：同一位會員的電話改了，有些表沒更新到；想查「某位會員上個月買了什麼」，要把幾十萬筆資料從頭翻到尾；兩位店員同時改同一筆庫存，其中一人的修改悄悄不見。

為了讓資料有規矩、查得快、又不會互相打架，軟體工程最常使用的起點就是**關聯式資料庫（Relational Database）**。

## 觀念

### 資料表、列與欄：有嚴格格式的表格

關聯式資料庫把資料存成一張一張的**資料表（Table）**，長得很像試算表：

- **欄位（Column）**：規定這張表有哪些屬性，以及每一格只能放什麼型別（例如「點數」只能是整數，「建立時間」只能是日期時間）。寫入不符合規則的資料時，資料庫會直接擋下來，避免髒資料混進系統。
- **資料列（Row）**：代表一筆具體的資料，例如「編號 501 的會員陳小美」。

這種「先講好每張表長什麼樣子」的規定，叫做**資料綱要（Schema）**。

### 主鍵與外鍵：把表和表串起來的線

為什麼不把會員、商品、訂單全部塞進同一張超級大表？因為會造成大量重複與混亂。關聯式資料庫的做法是把不同主題拆成不同的表，再用鑰匙串起來：

- **主鍵（Primary Key，簡稱 PK）**：每一張表用來「唯一辨識那一筆資料」的欄位，例如會員表的 `id = 501`。主鍵不能重複，也不能是空的。
- **外鍵（Foreign Key，簡稱 FK）**：在另一張表裡用來指向主鍵的欄位，例如訂單表裡的 `member_id = 501`。資料庫會幫忙把關：如果會員表裡根本沒有 501 號這個人，就不准建立 `member_id = 501` 的訂單，避免出現找不到主人的孤兒訂單。

比喻：把關聯式資料庫想成圖書館的卡片系統。「讀者登記簿」只記讀者編號、姓名、電話（主鍵是讀者編號）；「借閱紀錄簿」只記借閱編號、書號與讀者編號（外鍵指向讀者編號）。比喻的極限是：紙本登記簿需要館員自己翻兩本對照，關聯式資料庫則能一瞬間把兩張表合併查出結果，還會自動拒絕不存在的讀者編號。

### SQL：跟資料庫溝通的標準語言

要操作關聯式資料庫裡的資料，工程師使用的是 **SQL（Structured Query Language，結構化查詢語言）**。雖然不同廠牌的關聯式資料庫細節略有差異，但核心語法是共通的，主要做四件事：

- **新增（INSERT）**：顧客註冊時，在會員表加入一列。
- **查詢（SELECT）**：查出某位會員的所有訂單，甚至用 `JOIN` 把訂單表與會員表配對在一起看。
- **更新（UPDATE）**：顧客兌換點數後，扣減會員表的點數欄位。
- **刪除（DELETE）**：移除過期或取消的紀錄。

SQL 最大的特色是「你只要告訴資料庫**要什麼結果**，不用教它怎麼一行一行去硬碟裡翻找」，資料庫引擎會自己挑最快的方法去執行。

## 取捨

保存結構化商業資料時，關聯式資料庫與其他常見保存方式的比較：

| 做法 | 適合的情況 | 代價 |
|---|---|---|
| 關聯式資料庫 | 會員、訂單、帳務、庫存等結構固定且彼此有關聯的核心資料 | 欄位結構調整要經過遷移（migration）；單台寫入流量極大時擴展較費工 |
| 檔案／試算表 | 一次性匯出、小型靜態設定檔、非程式自動讀寫的人工報表 | 無法多人同時安全寫入；查詢大量資料慢；沒有外鍵與交易保護 |
| 非關聯式（NoSQL） | 格式經常變動、超高併發簡單讀寫或特殊資料形狀（見下一單元） | 多數不擅長複雜的跨表 JOIN 與嚴格的跨筆關聯約束 |

## 決策題

## 交給 AI 時要注意

- 請 AI 設計資料表時，先列出每個實體的主鍵與外鍵關係，並說明「如果刪除一筆會員，關聯的訂單該怎麼辦」。
- 提醒 AI 用資料庫本身的篩選與 `JOIN` 來查資料，不要把整張表撈回後端程式裡才用迴圈過濾。
- 檢查輸入參數的處理方式：務必使用參數化查詢（parameterized query），絕對不能把使用者輸入的文字直接拼進 SQL 字串裡，以免發生 SQL 注入攻擊。

## 重點回顧

- 關聯式資料庫用嚴格定義欄位的「資料表」保存資料，從源頭擋掉格式錯誤的資料。
- 主鍵唯一識別一筆資料，外鍵確保資料表之間的關聯不會指向不存在的對象。
- SQL 是操作關聯式資料庫的標準語言，擅長多條件篩選與跨表合併查詢（JOIN）。
- 只要資料結構清楚、重視正確性與關聯（例如訂單、會員、帳務），關聯式資料庫通常是首選。
