## 情境

學會關聯式資料庫後，Example Retail 的工程師一開始嚴格遵守「資料絕不重複」的原則，把所有東西拆成十幾張表。結果很快遇到兩個新問題：第一，商品漲價後，連帶讓舊訂單的金額跟著變了；第二，畫一個訂單列表頁要 `JOIN` 六張表，或是用開發工具寫一寫，背後竟然偷偷對資料庫發了上百次查詢，頁面慢到不行。

資料到底該拆得多細？而工程師常用來操作資料庫的工具 **ORM**，又幫了什麼忙、藏了什麼陷阱？

## 觀念

### 正規化：把資料拆乾淨，消滅重複與矛盾

**正規化（Normalization）** 是一套整理資料表的原則，核心精神只有一句話：**同一份事實只存在一個地方**。例如：會員的姓名與手機只放在「會員表」，訂單表只記錄 `member_id`。這樣做有兩個好處：

- **不會改漏**：會員改電話只改一筆，所有地方查出來都一致。
- **省空間、好維護**：不用在每張訂單重複寫同一段會員地址。

### 反正規化：為了速度或歷史快照，刻意重複存一份

既然正規化這麼好，為什麼有時候又要反過來？**反正規化（Denormalization）** 是在清楚知道代價的前提下，刻意把某些欄位複製一份放到另一張表裡，常見原因有兩個：

1. **保存當下快照**：訂單成立當下的「商品名稱」與「成交單價」必須複製一份存在訂單明細裡，否則日後商品改名或漲價，歷史訂單就會錯亂。
2. **加快讀取速度**：如果某個首頁看板每次都要把五張大表 `JOIN` 在一起算「今日總消費額」，在高流量下資料庫會很吃力，這時可以另外存一份算好的總額欄位，用空間與寫入時的同步成本，換取讀取時一瞬間拿到結果。

比喻：正規化像把通訊錄集中寫在一張電話表，所有人要打電話都來查這張表；反正規化像在每個部門的緊急聯絡單上都抄一份廠長的手機號碼，打起來很快也不用跨部門問，但廠長換號碼時，每張聯絡單都要記得改。比喻的極限是：歷史訂單裡的成交價「本來就不該跟著改」，這種反正規化甚至連同步更新都不需要。

### ORM：讓後端程式用「物件」操作資料表

寫後端程式時，工程師常用程式語言裡的「物件」（例如一個 `Order` 物件），而資料庫裡存的是一列一列的「資料表」。**ORM（Object-Relational Mapping，物件關聯對映）** 就是夾在兩者之間的翻譯工具：讓工程師用熟悉的程式語法去新增、修改物件，ORM 在背後自動幫你翻譯成 SQL 去跟資料庫溝通。

ORM 的好處是開發速度快、比較不容易打錯欄位名稱，也常內建防 SQL 注入的保護。但它也有兩個著名陷阱：

- **N+1 查詢問題**：先用 1 次查詢撈出 50 筆訂單，接著在程式迴圈裡每讀到一筆訂單的會員名稱，ORM 就偷偷再發 1 次 SQL 去查會員表，總共發了 51 次資料庫請求，網路往返把效能拖垮。
- **複雜查詢寫不好**：遇到多層統計報表或大量批次更新時，ORM 自動產生的 SQL 有時很笨重，效能不如工程師直接寫一段精簡的 SQL。

設計資料表時通常「先正規化、再視需求反正規化」：先把核心資料切乾淨，確定哪裡是查詢瓶頸或需要歷史快照，再有意識地保留冗餘。

## 取捨

資料拆合與操作方式的常見選擇：

| 做法 | 適合的情況 | 代價 |
|---|---|---|
| 高度正規化 | 寫入頻繁、重視資料一致性、不能容忍改漏一處的核心主檔（會員、商品主檔） | 跨越多張表查詢時需要 JOIN，高流量讀取可能較吃力 |
| 適度反正規化 | 歷史快照（訂單成交價、寄件地址）、高頻讀取但極少變動的統計欄位 | 資料重複佔空間；如果是會變動的欄位，必須確保更新時兩邊同步 |
| 使用 ORM 操作 | 一般增刪改查、快速開發、團隊希望統一資料存取寫法 | 容易不小心寫出 N+1 查詢；複雜報表與大量批次處理效能較差 |
| 直接寫 SQL | 複雜統計報表、效能關鍵查詢、需要精細控制資料庫行為的場景 | 程式碼較繁瑣，要自己處理資料表結構與程式物件的轉換 |

## 決策題

## 交給 AI 時要注意

- 設計訂單、發票、點數明細這類紀錄時，提醒 AI 區分「會隨主檔變動的參照（用外鍵）」與「當時的歷史快照（直接複製欄位值）」。
- 請 AI 用 ORM 寫列表查詢時，明確要求它處理關聯預先載入（eager loading），避免出現 N+1 查詢。
- 遇到複雜報表或大量批次更新，允許並要求 AI 評估是否改用原生 SQL，而不是硬用 ORM 寫出低效的迴圈。

## 重點回顧

- 正規化讓同一份事實只存一處，避免更新遺漏與資料矛盾，是資料庫設計的起點。
- 反正規化是為了歷史快照（如成交價）或讀取效能，有意識地保留重複欄位。
- ORM 把程式物件翻譯成 SQL，能加速日常開發，但要小心 N+1 查詢與複雜查詢的效能陷阱。
- 實務上常混用：日常操作用 ORM，效能關鍵或複雜報表直接寫 SQL。
