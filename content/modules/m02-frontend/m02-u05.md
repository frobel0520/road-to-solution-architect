## 情境

週年慶前，Example Retail 的行銷主管用自己的手機打開首頁，數到六才看到主視覺。他問：「是不是伺服器太慢，要多買幾台？」

這是很常見的直覺，但顧客感受到的速度，大部分不是花在伺服器上，而是花在「把檔案送到手機、再由手機變成畫面」的這段路上。這段路屬於前端，改善的方法也和加伺服器完全不同。

## 觀念

### 時間花在哪裡

從顧客點下連結到看見畫面，時間大致花在四個地方：

1. **連線與等待伺服器回應。** DNS 查詢、建立連線、伺服器產生 HTML（模組 1）。
2. **下載檔案。** HTML、CSS、JavaScript、圖片、字型。檔案越大、數量越多、網路越慢，就越久。
3. **瀏覽器處理。** 讀 HTML、等 CSS、執行 JavaScript、排版、繪製（本模組第 1 單元）。手機的運算能力比電腦弱，同樣的 JavaScript 會慢上許多。
4. **等更多資料。** 如果內容要靠 JavaScript 再向伺服器要資料才出現（例如 SPA），還要再等一輪。

第 2、3 項常常才是時間花最多的地方，但每個網站不同，所以要先量測，再決定改哪裡。

### 用什麼衡量「快」

「感覺很慢」沒辦法改善，要先變成數字。常用的指標有三個，量的是顧客實際感受到的三件事：

| 指標 | 量的是什麼 | 顧客的感受 |
|---|---|---|
| LCP（Largest Contentful Paint，最大內容繪製） | 畫面中最大的那塊內容多久出現 | 「我要看的東西出來了沒」 |
| INP（Interaction to Next Paint，互動到下一次繪製） | 點擊或輸入之後，畫面多久有反應 | 「按了有沒有反應」 |
| CLS（Cumulative Layout Shift，累計版面位移） | 載入過程中內容被推移了多少 | 「畫面會不會亂跳」 |

這三項合稱 Core Web Vitals。依 web.dev 的建議，要讓至少 75% 的頁面瀏覽達到：LCP 在 2.5 秒以內、INP 在 200 毫秒以內、CLS 在 0.1 以下。

量測有兩種來源：在自己的電腦上用工具模擬，可以馬上知道結果，適合開發時檢查；從真實顧客的瀏覽器收集，才知道各種手機與網路下的實際狀況。兩種都需要。

### 常見的改善方式

**讓要下載的東西變少、變小**

- 圖片通常是最大的檔案：依顯示尺寸提供大小合適的版本，使用壓縮率較高的格式。
- 畫面下方還看不到的圖片，等顧客快捲到時才載入（延遲載入）。
- JavaScript 只送這一頁用得到的部分；檢查第三方程式（廣告、統計、客服視窗）是否都還需要。
- 文字檔（HTML、CSS、JavaScript）在傳輸時壓縮。

**讓檔案離顧客近、不要重複下載**

- 靜態檔案放到 CDN（模組 1 第 5 單元）。
- 設定瀏覽器快取：告訴瀏覽器這個檔案可以保留多久，下次造訪就不用重新下載。常見做法是檔名裡帶有內容的版本，內容改了檔名就變，舊的可以放心保留很久。

**不要擋住第一個畫面**

- CSS 精簡，先載入第一個畫面需要的部分。
- 不急的 JavaScript 延後執行，讓瀏覽器先把畫面畫出來。
- 重要的內容直接放在 HTML 裡，不要等 JavaScript 去要（本模組第 2 單元談的靜態網站與 SSR）。

**不要讓畫面跳動**

- 圖片、廣告、之後才載入的區塊，事先在版面上保留空間。

比喻：像搬家。箱子少一點、小一點（減少檔案），倉庫離新家近一點（CDN），上次搬過的不用再搬（快取），先搬床和冰箱、裝飾品晚點再說（先載入重要的）。比喻不準的地方是：搬家只搬一次，網頁是每位顧客、每次造訪都在搬，所以每省一點都會被放大很多倍。

## 取捨

改善效能都有代價，下面是幾個常見的選擇：

| 做法 | 適合的情況 | 代價 |
|---|---|---|
| 圖片縮小與轉檔、延遲載入 | 圖片多的頁面，幾乎都該先做 | 要有產生多種尺寸的流程；壓過頭畫質會變差 |
| 長時間的瀏覽器快取 | 很少變動的靜態檔案 | 檔名沒有帶版本的話，更新後顧客會繼續用到舊檔 |
| 減少或延後 JavaScript | 手機上反應慢、第一個畫面晚 | 延後的功能比較晚才能用；要取捨哪些第三方程式可以拿掉 |
| 改成靜態網站或 SSR | 內容要等 JavaScript 才出現，是主要瓶頸 | 架構要調整，是幾項裡工程最大的 |

## 決策題

## 交給 AI 時要注意

- 先給它量測結果（哪一頁、什麼裝置與網路、各指標多少），再請它提出改善方式，不要只說「讓網站變快」。
- 訂出具體的目標與預算，例如某一頁在手機上的 LCP 上限、單頁 JavaScript 的大小上限，並要求每次修改後回報量測數字。
- 檢查它新增的套件有多大、是不是每一頁都會載入。
- 要求圖片與之後才載入的區塊都保留空間，並在慢速網路的設定下實際看一次載入過程。

## 重點回顧

- 顧客感受到的速度，多半花在下載檔案與瀏覽器處理，而不是伺服器。
- 用 LCP、INP、CLS 把「快不快」變成數字，先量測再改善。
- 圖片與 JavaScript 是最常見的瓶頸：減少、縮小、延後。
- CDN 與瀏覽器快取讓檔案離顧客近、不用重複下載。
- 替晚到的內容預留空間，畫面才不會跳動。
