## 情境

Example Retail 的工程師把網站和 API 分開放在兩個網址之後，網站突然抓不到資料，瀏覽器的開發者工具裡出現一行紅字，寫著 CORS。更奇怪的是，同一個 API 網址直接貼到網址列卻打得開。

這不是故障，是瀏覽器刻意擋下來的。要知道怎麼正確地放行，得先知道瀏覽器在防什麼。

## 觀念

### 如果瀏覽器不設限

上一個單元說過，瀏覽器會自動把 Cookie 附在發給那個網站的請求上。假設顧客登入了 Example Retail，接著在另一個分頁打開一個惡意網站。那個網站的 JavaScript 可以悄悄對 Example Retail 發出「查詢我的訂單」的請求，瀏覽器會自動附上顧客的登入 Cookie，伺服器以為是顧客本人，就回傳了訂單與地址。

如果惡意網站的 JavaScript 能讀到這份回應，它就偷到資料了。而顧客什麼都沒做，只是開了一個網頁。

### 同源政策：預設不能讀別人家的回應

為了防止這種事，瀏覽器有一條基本規則，叫做**同源政策（Same-Origin Policy）**：網頁的 JavaScript 只能讀取「和自己同一個來源」的回應。

**來源（origin）** 由三個部分組成：協定、主機名稱、port。三個都一樣才算同源。

| 和 https://shop.example.com 比較 | 是否同源 | 原因 |
|---|---|---|
| https://shop.example.com/cart | 是 | 只有路徑不同 |
| http://shop.example.com | 否 | 協定不同 |
| https://api.example.com | 否 | 主機名稱不同 |
| https://shop.example.com:8443 | 否 | port 不同 |

所以情境裡的問題就是：shop.example.com 的網頁，想讀 api.example.com 的回應，兩者不同源，瀏覽器不給讀。直接在網址列打開 API 沒有問題，因為那是顧客自己前往那個網址，不是某個網頁的程式在背後代替他讀取。

### CORS：由對方伺服器說「這個來源可以」

網站和 API 放在不同來源是很常見的做法，所以需要一個正式的放行方式，這就是 **CORS（Cross-Origin Resource Sharing，跨來源資源共用）**。

做法是讓**被呼叫的那一方**決定：

1. 瀏覽器發出跨來源請求時，會附上一個標頭，寫明「這個請求來自 https://shop.example.com」。
2. API 伺服器在回應裡加上一個標頭，寫明它允許哪個來源讀取。
3. 瀏覽器比對：允許的來源包含目前的網頁，才把回應交給 JavaScript；否則丟掉，並在開發者工具顯示 CORS 錯誤。

對於會修改資料或帶有特殊標頭的請求，瀏覽器還會先發一個「預檢請求（preflight）」，問伺服器「我可以送這種請求嗎」，得到允許才送出真正的請求。

比喻：像大樓的訪客登記。管理員（瀏覽器）會問住戶（API 伺服器）「這位訪客可以上去嗎」，住戶說可以才放行。比喻不準的地方是：這位管理員只管走大門的人。不走瀏覽器的程式，根本不會經過他。

### CORS 不是什麼

這是最容易誤會的地方：

- **CORS 不是用來保護伺服器的。** 它保護的是使用者，避免他的登入身分被別的網站借用來讀資料。不透過瀏覽器的程式可以直接呼叫 API，CORS 管不到。API 要保護自己，靠的是驗證身分與權限。
- **CORS 錯誤不能從前端修。** 決定權在被呼叫的伺服器，前端的程式怎麼改都沒用。
- **被擋的是「讀取回應」，請求不一定沒送出去。** 簡單的請求可能已經到了伺服器並被執行，只是網頁讀不到結果。所以會修改資料的操作，還需要別的防護，例如上一個單元提到的 Cookie SameSite 設定。

## 取捨

網站需要呼叫不同來源的 API 時：

| 做法 | 適合的情況 | 代價 |
|---|---|---|
| API 只允許指定的來源 | 自己的網站呼叫自己的 API，尤其是帶登入身分的 | 每多一個網站（例如測試環境、活動網站）就要更新名單 |
| API 允許所有來源 | 完全公開、不帶登入身分的資料，例如門市清單 | 任何網站都能讀；不能和登入身分一起使用 |
| 用反向代理把網站與 API 放在同一個來源 | 想完全避開跨來源問題，例如 /api/ 轉給 API 服務 | 多一層轉送；所有流量都經過同一個入口（模組 1 第 5 單元） |

## 決策題

## 交給 AI 時要注意

- 明確列出允許的來源（正式、測試環境各是哪些網址），不要接受「先設成允許全部，之後再改」。
- 遇到 CORS 錯誤時，提醒它修改的是被呼叫的 API 伺服器設定，不要在前端繞過，也不要另外架一個不檢查來源的轉送服務。
- 要求每個 API 都自己驗證身分與權限，不可以把 CORS 當成存取控制。
- 完成後請它用不在名單上的來源測試一次，確認瀏覽器會擋下。

## 重點回顧

- 來源由協定、主機名稱、port 三者決定；三個都相同才是同源。
- 同源政策讓網頁的 JavaScript 預設讀不到其他來源的回應，保護使用者的登入身分不被借用。
- CORS 由被呼叫的伺服器設定，告訴瀏覽器哪些來源可以讀取回應。
- CORS 只在瀏覽器裡生效，不能取代 API 的身分驗證與權限檢查。
