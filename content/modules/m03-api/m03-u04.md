## 情境

到目前為止談的 API，都是「一方問、另一方答」：App 問訂單狀態，伺服器回答。可是很多時候，想知道消息的一方並不知道事情什麼時候會發生。

Example Retail 遇到三個這樣的需求：物流商的包裹送達時要更新訂單、週年慶的商品頁要即時顯示剩餘數量、線上客服要能和顧客即時對話。如果只會「問與答」，就只能一直問「好了沒？好了沒？」。這個單元要談的是：誰主動、連線開多久，有哪些選擇。

## 觀念

### Polling：每隔一段時間問一次

**Polling（輪詢）** 是最直接的做法：想知道消息的一方，每隔固定時間發一次請求問「有新的嗎」。

好處是什麼都不用改，用一般的 API 就能做。壞處是兩難：問得太勤，大部分的請求都得到「沒有」，白費雙方的資源；問得太疏，消息就晚到。

### Webhook：有事的時候，對方呼叫你

**Webhook** 把方向反過來：想知道消息的一方先提供一個網址，事情發生時，由對方主動對這個網址發出請求。有人叫它「反向 API」。

以物流為例：Example Retail 把「接收物流通知」的網址登記給物流商，包裹狀態一變，物流商的伺服器就呼叫這個網址，把訂單編號與新狀態送過來。

Webhook 是伺服器對伺服器的做法，因為接收的一方必須有固定的網址、隨時在線。使用時有三件事一定要處理：

- **驗證來源。** 這個網址是公開的，任何人都可以對它發請求、假冒物流商。常見的做法是雙方共享一組密鑰，對方用它替每則通知算出簽章，接收方驗證簽章正確才處理。
- **可能重複。** 對方沒收到「收到了」的回應時通常會重送，所以同一則通知可能來兩次，處理時要能認出重複的。
- **可能漏掉。** 接收方故障時通知可能遺失，重要的資料要有補救方式，例如定期用查詢對帳。

### SSE：伺服器對瀏覽器的單向推送

瀏覽器沒有固定網址，伺服器沒辦法主動連過去，所以 webhook 不能用在網頁上。要讓伺服器主動把資料送到瀏覽器，必須由瀏覽器先開一條連線，並且**不要關**。

**SSE（Server-Sent Events，伺服器傳送事件）** 就是這樣：瀏覽器發出一個一般的 HTTP 請求，伺服器不結束回應，有新資料就接著往下送。資料只能從伺服器流向瀏覽器。斷線時瀏覽器會自動重連。

它適合「伺服器有消息要一直告訴瀏覽器」的場合：剩餘數量、訂單進度、通知。

### WebSocket：雙向的長連線

**WebSocket** 也是由瀏覽器發起，但連線建立之後會切換成另一種通訊協定，雙方都可以隨時主動送訊息給對方，延遲很低。

它適合雙向、頻繁的互動：客服對話、多人同時編輯、即時協作。代價是比較複雜：斷線重連、身分驗證、訊息格式都要自己處理；中間的代理與負載平衡也要支援並調整設定。

比喻：polling 是每十分鐘打一次電話問「到貨了嗎」；webhook 是留下電話，到貨時店家打給你；SSE 是打開收音機聽廣播，只能聽；WebSocket 是一通不掛斷的電話，雙方隨時可以講。比喻不準的地方是：電話和廣播一次只服務少數人，伺服器卻要同時維持成千上萬條連線，每一條都占用資源，這是選擇長連線時最主要的成本。

### 先問兩個問題

1. **誰需要被通知？** 另一台伺服器，還是使用者的瀏覽器或 App？前者可以用 webhook，後者要用 polling、SSE 或 WebSocket。
2. **多即時？方向？** 晚幾分鐘沒關係就用 polling；只要伺服器往用戶端送就用 SSE；雙方都要主動送才用 WebSocket。

四列由上到下是四種做法，箭頭的方向代表誰主動送出訊息。注意第二列的兩端都是伺服器；第三、四列的左邊是瀏覽器，連線都由瀏覽器先發起，差別在建立之後資料可以往哪個方向流。

## 取捨

| 做法 | 適合的情況 | 代價 |
|---|---|---|
| Polling | 變動不頻繁，或晚一點知道沒關係；對方只提供一般 API | 大多數請求是白問；間隔決定了延遲 |
| Webhook | 伺服器對伺服器的事件通知，例如物流、金流的結果 | 要有公開網址；要驗證來源、處理重複與遺漏 |
| SSE | 伺服器要持續把更新送到瀏覽器，單向 | 伺服器要維持大量開著的連線；只能單向 |
| WebSocket | 雙向、頻繁、低延遲的互動，例如對話與協作 | 最複雜；連線、重連、驗證都要自己處理；中間的設備要支援 |

## 決策題

## 交給 AI 時要注意

- 先說明資料多久變一次、晚多久看到可以接受、需不需要雙向，再請它選做法；沒有即時需求時明確要求不要用長連線。
- 接收 webhook 時，要求驗證簽章、能辨認重複的通知，並且先回應「收到」再做耗時的處理。
- 用 SSE 或 WebSocket 時，要求說明斷線重連後怎麼補上漏掉的訊息，以及連線時怎麼驗證身分。
- 要求估算尖峰時同時在線的連線數，並確認負載平衡等中間設備的逾時設定。

## 重點回顧

- Polling 由用戶端定時詢問，簡單但浪費，延遲取決於間隔。
- Webhook 是伺服器對伺服器的反向呼叫，要驗證來源並處理重複與遺漏。
- SSE 是伺服器對瀏覽器的單向推送；WebSocket 是雙向的長連線。
- 伺服器無法主動連到瀏覽器，所以網頁上的即時更新都由瀏覽器先發起連線。
- 先問資料多久變一次、晚到有沒有關係；不需要即時就用一般的請求與回應。
