## 情境

上一個單元說 API 是合約。但合約總要有個寫法：功能要怎麼命名？查詢和修改怎麼區分？成功或失敗怎麼表示？資料用什麼格式？

如果每個 API 都自己發明一套，使用的人每接一個就要重學一次。Example Retail 的團隊決定和大多數網站一樣，採用最普遍的組合：用 REST 的風格設計 API，用 JSON 當資料格式。

## 觀念

### REST：把 HTTP 本來就有的東西拿來用

模組 1 第 4 單元介紹過 HTTP：請求有方法與網址，回應有狀態碼。**REST（Representational State Transfer，表現層狀態轉移）** 不是一種新技術，而是一種設計風格：直接用 HTTP 既有的這些零件來表達 API，不另外發明。

它有三個核心想法。

**一、網址代表「資源」，是名詞**

資源（resource）就是系統裡的東西：會員、訂單、商品。每個資源有自己的網址。

| 網址 | 代表 |
|---|---|
| /orders | 所有訂單 |
| /orders/1001 | 編號 1001 的那筆訂單 |
| /members/12345/orders | 會員 12345 的所有訂單 |

**二、HTTP 方法代表「要做什麼」，是動詞**

| 方法 | 意思 | 例子 |
|---|---|---|
| GET | 讀取，不改變任何資料 | GET /orders/1001　查這筆訂單 |
| POST | 新增 | POST /orders　建立一筆新訂單 |
| PUT | 整筆取代 | PUT /orders/1001　用新內容取代整筆訂單 |
| PATCH | 修改一部分 | PATCH /orders/1001　只改收件地址 |
| DELETE | 刪除 | DELETE /orders/1001　刪除這筆訂單 |

所以同一個網址 /orders/1001，搭配不同的方法就是不同的操作。

這裡有個重要的約定：**GET 不可以改變資料。** 瀏覽器、快取、搜尋引擎都相信這件事，會自動重送或預先發出 GET 請求。另外，GET、PUT、DELETE 重複送幾次，結果都和送一次相同；POST 重複送，則可能建立出好幾筆。這個差別在網路不穩、需要重試時很重要（本模組第 5 單元）。

**三、狀態碼代表「結果如何」**

| 範圍 | 意思 | 常見的例子 |
|---|---|---|
| 2xx | 成功 | 200 成功、201 已建立 |
| 3xx | 要去別的地方 | 301 永久搬到新網址 |
| 4xx | 請求這一端的問題 | 400 格式錯誤、401 尚未登入、403 沒有權限、404 找不到 |
| 5xx | 伺服器這一端的問題 | 500 伺服器內部錯誤、503 暫時無法服務 |

使用的程式只要看第一個數字，就知道該不該重試、該怪誰：4xx 再送一次也不會成功，要修正請求；5xx 可以稍後再試。

還有一個原則是**無狀態（stateless）**：每個請求都要帶齊伺服器處理它所需的資訊（包括身分憑證），伺服器不依賴「上一個請求說過什麼」。這樣任何一台伺服器都能處理任何一個請求，方便用負載平衡分流。

### JSON：人和程式都讀得懂的資料格式

**JSON（JavaScript Object Notation）** 是一種用純文字表示資料的格式。它只有幾種積木：

| 積木 | 寫法 | 例子 |
|---|---|---|
| 物件 | 大括號，裡面是「名稱：值」的組合 | 一筆訂單 |
| 陣列 | 中括號，裡面是依序排列的值 | 訂單裡的多個品項 |
| 字串 | 雙引號包起來的文字 | "已出貨" |
| 數字 | 直接寫 | 1280 |
| 布林值 | true 或 false | 是否使用點數 |
| 空值 | null | 尚未填寫的備註 |

積木可以一層套一層。下面用表格表示一筆訂單的 JSON 會有哪些內容：

| 名稱 | 值 | 類型 |
|---|---|---|
| id | 1001 | 數字 |
| status | "shipped" | 字串 |
| usePoints | true | 布林值 |
| note | null | 空值 |
| items | 兩個品項，每個品項有 name 與 quantity | 陣列，裡面是物件 |

JSON 普及的原因是簡單：幾乎所有程式語言都能讀寫，人也看得懂。代價是它不檢查內容：欄位少了、數字被寫成字串，JSON 本身不會抱怨，要靠 API 的規格與程式另外驗證。它也沒有日期與金額的專用類型，日期通常用約定好格式的字串表示，金額要約定單位與小數的處理方式。

比喻：REST 像是大家約定好的表單格式（哪一欄填對象、哪一欄填動作），JSON 是表單上填寫內容用的文字。比喻不準的地方是：REST 只是慣例，沒有人強制檢查，所以不同團隊做出來的「REST API」細節常常不一樣。

## 取捨

設計 REST API 時常見的幾個選擇：

| 選擇 | 好處 | 代價 |
|---|---|---|
| 照 REST 慣例（名詞網址、標準方法與狀態碼） | 使用者不用學就看得懂；快取、監控等工具能直接配合 | 不是每個操作都能自然地對應成「資源的新增修改刪除」，例如「結帳」「重送通知信」 |
| 所有操作都用 POST 加動詞網址 | 設計時不用思考資源怎麼切 | 失去 GET 的快取與安全假設；每個 API 都要另外說明 |
| 一個 API 回傳很完整的資料 | 使用者一次拿齊，請求次數少 | 用不到的欄位也要傳，手機網路上比較慢 |
| 多個 API 各回傳一小部分 | 每個回應都小 | 一個畫面要發很多次請求（下一個單元會談這個問題） |

## 決策題

## 交給 AI 時要注意

- 給它資源清單與命名規則（網址用複數名詞、欄位命名風格），並要求整個 API 一致。
- 明確要求讀取用 GET 且不可改變資料；會改變資料的操作不可以用 GET。
- 要求列出每個 API 會回哪些狀態碼、各在什麼情況，並檢查有沒有「失敗卻回 200」。
- 約定日期與金額在 JSON 裡的表示方式，並要求伺服器驗證收到的 JSON，不能假設格式一定正確。

## 重點回顧

- REST 是設計風格：網址是資源（名詞），HTTP 方法是動作（動詞），狀態碼是結果。
- GET 只能讀取；會改變資料的操作用 POST、PUT、PATCH、DELETE。
- 狀態碼看第一個數字：2xx 成功、4xx 請求有問題、5xx 伺服器有問題。
- JSON 用物件、陣列、字串、數字、布林值、空值組成資料，簡單通用，但本身不驗證內容。
