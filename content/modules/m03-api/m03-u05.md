## 情境

Example Retail 的 API 上線幾個月後，團隊發現平常沒問題的東西，在三種時候會出事：**出錯的時候**，App 不知道該怎麼辦，只能顯示「發生錯誤」；**要改版的時候**，一改就有人的程式壞掉；**流量異常的時候**，一個使用者就能拖垮所有人。

這三件事在設計 API 時最容易被跳過，因為「正常情況」不會遇到。這個單元談的就是合約裡關於不正常情況的條款。

## 觀念

### 錯誤回應：讓對方知道接下來該怎麼做

一個好的錯誤回應要回答三個問題：出了什麼事？是誰的問題？再試一次有沒有用？

狀態碼回答了大方向（本模組第 2 單元）：4xx 是請求的問題，改了再送；5xx 是伺服器的問題，可以稍後再試。但狀態碼不夠細，所以回應本文還要有固定的格式，通常包含：

| 欄位 | 用途 | 例子 |
|---|---|---|
| 錯誤代碼 | 給程式判斷用，固定不變 | INSUFFICIENT_POINTS |
| 訊息 | 給人看的說明 | 點數不足，目前有 120 點，需要 300 點 |
| 追蹤編號 | 客服與工程師查紀錄用 | 一串唯一的編號 |

兩個要注意的地方：

- **所有 API 的錯誤格式要一致。** 使用者只要寫一套處理邏輯。
- **不要洩漏內部細節。** 資料庫的錯誤訊息、程式的堆疊內容、伺服器路徑，對使用者沒用，對攻擊者很有用。詳細內容記在伺服器的紀錄裡，用追蹤編號對應。

### 重試與冪等：同一件事做兩次也沒關係

網路不可靠。請求可能沒送到，也可能送到了、處理完了，但回應在回來的路上遺失。對送出請求的一方來說，這兩種情況看起來一樣：等不到回應。

如果操作是「查詢訂單」，再送一次沒有壞處。如果是「建立訂單」或「扣款」，再送一次就可能做兩次。

**冪等（idempotent）** 的意思是：同一個操作做一次和做很多次，結果相同。GET、PUT、DELETE 天生如此，POST 不是。讓 POST 也能安全重試的常見做法是**冪等鍵（idempotency key）**：用戶端替每一次「意圖」產生一個唯一的識別碼，隨請求送出；伺服器記下處理過的識別碼，再看到同一個就不重做，直接回傳上次的結果。

比喻：像匯款單上的流水號。銀行看到同一個流水號出現第二次，知道是重複的單子，不會再匯一次。比喻不準的地方是：伺服器不會永遠保存這些識別碼，通常只保留一段時間，所以它保護的是「短時間內的重試」。

### 版本：改合約而不毀約

本模組第 1 單元說過，移除欄位、改名、改變意義都是破壞性變更。API 總會需要這類改動，版本管理就是讓新舊可以並存的方法。

- **能不出新版就不出。** 新增欄位、新增功能不會破壞任何人，直接加上去就好。
- **真的要做破壞性變更，就開新版本，舊版繼續運作。** 最常見的標示方式是把版本放在網址裡，例如 /v1/orders 與 /v2/orders；也有放在請求標頭裡的做法。
- **舊版要有退場計畫。** 公告停用日期、主動通知使用者、觀察舊版還有多少流量，到期才關閉。同時維護的版本越多，成本越高。

### 限流：保護自己，也保護其他使用者

**限流（rate limiting）** 是限制每個使用者在一段時間內可以發出多少請求，例如每個 API 金鑰每分鐘若干次。超過時，伺服器不處理，直接回狀態碼 429（請求過多），並告知多久之後可以再試。

它保護三件事：

- **伺服器本身**：不會被突然暴增的請求壓垮。
- **其他使用者**：一個人的程式出錯或濫用，不會讓所有人變慢。
- **成本**：有些操作很貴（例如寄簡訊、複雜的查詢），需要上限。

限流通常設在入口，例如反向代理或 API 閘道（API gateway，專門放在 API 前面，集中處理驗證、限流與紀錄的元件），這樣被擋下的請求不會消耗後端的資源。

使用 API 的一方也有責任：收到 429 或 5xx 時不要立刻重試，而是等一下再試，而且每次失敗後等更久，並加上一點隨機的時間差。否則伺服器一恢復，所有人同時重試，又會把它壓垮。

## 取捨

| 選擇 | 適合的情況 | 代價 |
|---|---|---|
| 只做相容的變更，不分版本 | 內部 API、使用者可以協調 | 設計上的舊包袱會一直累積 |
| 版本放在網址（/v1/、/v2/） | 對外 API；想讓版本一眼看得出來 | 同時維護多個版本；要有退場流程 |
| 依金鑰限流 | 有多個外部使用者或合作廠商 | 要決定合理的額度；正常的大客戶可能被誤擋，要能調整 |
| 冪等鍵 | 會扣款、建立訂單、寄送通知等不能重複的操作 | 伺服器要保存處理過的識別碼與結果；用戶端要配合產生 |

## 決策題

## 交給 AI 時要注意

- 先定好全站一致的錯誤格式（錯誤代碼、訊息、追蹤編號），要求每個 API 都照用，並檢查回應裡有沒有洩漏資料庫或程式的內部訊息。
- 列出哪些操作不能重複執行，要求用冪等鍵處理，並請它寫測試：同一個請求送兩次，只能成立一筆。
- 修改既有 API 時，要求它判斷是否為破壞性變更；是的話開新版本，不可以直接改舊版。
- 要求說明限流的額度依據、超過時回什麼，以及用戶端重試時的等待方式。

## 重點回顧

- 錯誤回應要有一致的格式，讓對方知道出了什麼事、能不能重試，但不洩漏內部細節。
- 等不到回應不代表沒成功；不能重複的操作要用冪等鍵，才能安全重試。
- 相容的變更直接加；破壞性變更開新版本，舊版公告期限後才退場。
- 限流讓單一使用者的失控不會拖垮所有人，超過時回 429。
- 重試要越等越久並加上隨機時間差，避免同時湧回來。
