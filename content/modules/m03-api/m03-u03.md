## 情境

Example Retail 的 REST API 上線後，大部分時候運作良好，但有兩個地方開始讓團隊覺得卡卡的。

第一個是 App 首頁：一個畫面要呼叫四個 API，拿回來的資料大半用不到。第二個是後端內部：結帳時幾個服務之間來回呼叫十幾次，每次都要把資料轉成 JSON 文字再解析回來。有人提議換成 GraphQL，有人提議換成 gRPC。這兩個不是 REST 的升級版，而是針對不同問題的另外兩種做法。

## 觀念

### REST 在什麼地方會不順

REST 以「資源」為單位，一個網址回傳一種資源的固定內容。這帶來兩個常見的問題：

- **拿太多（over-fetching）**：只需要訂單狀態，API 卻回傳整筆訂單的三十個欄位。
- **拿太少（under-fetching）**：一個畫面需要會員、訂單、商品，要呼叫好幾個 API 才湊得齊。

在手機網路上，每多一次請求、每多傳一些資料，顧客都感覺得到。

### GraphQL：由用戶端決定要什麼

**GraphQL** 是一種 API 的查詢語言。它把選擇權交給使用 API 的一方（用戶端）：

- 伺服器先用 **schema** 定義有哪些資料類型、每個類型有哪些欄位、彼此怎麼關聯。schema 有嚴格的型別。
- 用戶端在請求裡寫明「我要會員的等級與點數、最近三筆訂單的狀態」，伺服器就只回這些，形狀和請求的一模一樣。
- 所有請求通常都送到同一個網址，不像 REST 一個資源一個網址。

比喻：REST 像套餐，每個套餐的內容是固定的，想吃三個套餐裡的各一樣，就得點三份。GraphQL 像自助餐，拿一個盤子，自己夾要的。比喻不準的地方是：自助餐的菜是事先煮好的，GraphQL 的每一樣資料都是伺服器當場去準備的，客人夾得越多、越深，廚房越忙。

它的代價也來自這份彈性：

- **伺服器比較複雜。** 用戶端可以寫出層層巢狀、非常昂貴的查詢，伺服器要限制查詢的深度與成本。
- **快取比較難。** REST 的 GET 請求可以直接被瀏覽器與 CDN 快取；GraphQL 的查詢與修改都要支援用 POST 傳送，而 POST 預設不會被快取，要另外設計。
- **錯誤的表示方式不同。** 回應可能同時帶有部分資料與錯誤，狀態碼不像 REST 那樣一眼看得出成敗，監控要跟著調整。

### gRPC：像呼叫自己程式裡的功能一樣呼叫遠端

**gRPC** 是一套遠端程序呼叫（RPC，Remote Procedure Call）框架。RPC 的想法是：呼叫另一台機器上的功能，寫起來就像呼叫自己程式裡的功能。

- 先在一份 .proto 檔裡定義服務有哪些方法、每個方法的輸入與輸出長什麼樣子。
- 工具依這份定義，替不同的程式語言產生用戶端與伺服器端的程式碼。兩邊都照同一份定義，欄位名稱打錯、型別不對，在開發時就會被發現。
- 資料預設用 **Protocol Buffers** 格式傳送。它是二進位格式，比 JSON 文字精簡，但人沒辦法直接閱讀。
- 除了一問一答，還支援串流：伺服器連續回傳多筆、用戶端連續送出多筆，或雙方同時連續傳送。
- 用戶端可以指定願意等多久，超過就放棄。

它的代價：

- **不能直接看內容。** 除錯需要專門的工具，不像 JSON 貼到任何地方都看得懂。
- **瀏覽器要另外處理。** 網頁要透過 gRPC-Web 才能存取 gRPC 服務，官方教學的做法是在中間放一層代理來轉送。
- **雙方綁得比較緊。** 兩邊都要用產生出來的程式碼，介面一改就要重新產生並部署，適合自己掌控兩端的情況。

### 可以並存

三者並不互斥。常見的組合是：對外的公開 API 用 REST，因為最通用、任何人都會用；面對多種畫面的資料查詢用 GraphQL；後端內部服務之間用 gRPC。多一種做法就多一套工具與知識要維護，所以要有明確的問題才加，不是因為比較新。

## 架構圖

![三種做法的比較：REST 是用戶端向多個資源網址各發一次請求；GraphQL 是用戶端向單一網址送出一份寫明欄位的查詢；gRPC 是後端服務之間依共同的介面定義互相呼叫，傳送二進位資料](./m03-u03-styles.svg)

三列各是一種做法。REST 的 App 發了三次請求；GraphQL 只發一次，並在請求裡寫明要什麼；gRPC 畫的是後端兩個服務之間的呼叫，兩邊共用同一份介面定義。注意三者出現的位置不一樣：前兩個在用戶端與伺服器之間，第三個多半在伺服器與伺服器之間。

## 取捨

| 做法 | 適合的情況 | 代價 |
|---|---|---|
| REST 加 JSON | 對外公開或給合作夥伴的 API；資源單純的新增、查詢、修改、刪除；想讓快取直接生效 | 複雜畫面要多次請求；回應常有用不到的欄位 |
| GraphQL | 多種用戶端要的資料不同；一個畫面要組合多種資料；畫面常常改 | 伺服器要限制查詢成本；快取、監控、權限都要另外設計 |
| gRPC | 內部服務之間頻繁呼叫；要求低延遲與嚴格型別；需要串流 | 內容不能直接閱讀；瀏覽器要額外處理；兩端綁得緊 |

如果沒有遇到上面說的具體問題，REST 通常是最省力的起點。

## 決策題

## 交給 AI 時要注意

- 先說明誰會呼叫這個 API（瀏覽器、App、內部服務、外部廠商），再請它建議做法，並要求說明不選其他做法的理由。
- 用 GraphQL 時，要求限制查詢的深度與成本，並說明每個欄位的權限怎麼檢查。
- 用 gRPC 時，介面定義檔要先審過；要求每個呼叫都設定等待時間的上限。
- 不要因為它說「比較新」或「比較快」就換做法；要求它指出現在的做法實際遇到了什麼問題。

## 重點回顧

- REST 的常見問題是拿太多與拿太少，複雜畫面要呼叫好幾次。
- GraphQL 讓用戶端指定要哪些欄位，適合多種用戶端與多變的畫面；代價在伺服器端的複雜度與快取。
- gRPC 用共同的介面定義與二進位格式，適合內部服務之間的頻繁呼叫；代價是不易閱讀、瀏覽器要另外處理。
- 三者可以並存；沒有具體問題時，REST 是最省力的起點。
