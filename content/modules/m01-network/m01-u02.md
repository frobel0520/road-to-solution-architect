## 情境

上一個單元提到，資料會切成封包在網路上傳送。但網路並不完美：封包可能遺失、可能晚到、到達的順序也可能和送出時不一樣。

Example Retail 的收銀機把交易送回總部時，一筆都不能掉；但顧客在 App 看門市直播時，比起每一格畫面都完整，更在意畫面不要卡住。這兩種需求，對應到網路上兩種最基本的傳輸方式：TCP 與 UDP。

## 觀念

### TCP：可靠的傳送

**TCP（Transmission Control Protocol，傳輸控制協定）** 會在送資料前先和對方建立連線，確認雙方都準備好了。之後它保證三件事：

- **不遺失**：對方收到後會回覆確認，沒收到確認的封包會重送。
- **不亂序**：每個封包都有編號，對方會照順序組回去。
- **流量控制**：對方處理不過來時，會放慢送出的速度。

代價是比較慢：建立連線要先來回幾趟，遺失時要等重送，後面的資料也得排隊等前面補齊。網頁、API、檔案下載、電子郵件，大多建立在 TCP 上，因為少一個位元組，內容就錯了。

### UDP：快速、不保證

**UDP（User Datagram Protocol，使用者資料包協定）** 不建立連線，也不確認對方有沒有收到，直接把封包送出去。遺失了不補送，順序亂了也不管。

聽起來很不可靠，但在「晚到的資料等於沒用」的情況下，這反而是優點。視訊通話、線上遊戲、直播就是如此：晚了半秒才到的畫面已經過時，等它不如直接顯示下一格。

比喻：TCP 像掛號信，每封都要簽收，沒簽收就重寄；UDP 像現場廣播，講過就算了，沒聽到的人只能聽下一句。比喻不準的地方是：真實的應用常在 UDP 上自己加一點補救機制，例如只補送最重要的資料。

### 建立在 UDP 上的新方式

近年較新的網頁傳輸方式 HTTP/3，底層使用的 QUIC 就是建立在 UDP 上，再自己實作可靠傳送。原因是 TCP 的規則由作業系統實作，很難改；放在 UDP 上，就可以用比較新的方法減少連線等待時間。這說明 TCP 與 UDP 不是「好」與「壞」，而是兩種不同的起點。

## 取捨

| 選擇 | 適合的情況 | 代價 |
|---|---|---|
| TCP | 資料一個都不能掉：網頁、API、交易、檔案 | 建立連線與重送會增加延遲；網路差時會卡住等補送 |
| UDP | 即時比完整重要：直播、視訊、遊戲、頻繁回報的感測資料 | 遺失、重複、亂序都要由應用程式自己決定怎麼處理 |
| 建立在 UDP 上的新協定（例如 QUIC） | 想要可靠傳送，又想減少連線等待 | 比較新，部分網路設備或公司防火牆可能不支援，要準備退回 TCP |

## 重點回顧

- 網路上的封包可能遺失、延遲或亂序。
- TCP 保證不遺失、不亂序，代價是比較慢；網頁與 API 多半用 TCP。
- UDP 不保證送達，但不用等，適合「晚到等於沒用」的即時資料。
- 選擇的關鍵問題是：這份資料能不能掉？能不能等？
