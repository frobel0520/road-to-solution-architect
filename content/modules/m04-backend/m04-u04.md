## 情境

Example Retail 的網站和 App 都有登入功能。以前常聽人把「權限」和「登入」混在一起講：「他明明已經登入了，為什麼還是不能進後台？」「為什麼改一下網址上的數字，就看得到別人的訂單？」

登入只是這扇門的第一半。後端在放行任何一個動作之前，其實會經過兩道完全不同的檢查，搞混了其中一道，輕則功能卡住，重則造成嚴重的資料外洩。

## 觀念

### 認證 vs. 授權：你是誰，以及你能做什麼

在安全設計上，登入後的檢查一定分成兩步：

1. **認證（Authentication，簡稱 AuthN）**：確認「你是誰」。例如輸入帳號密碼、簡訊驗證碼，或用第三方帳號登入。通過認證後，系統知道你是「會員 5012」。如果失敗，HTTP 通常回傳 `401 Unauthorized`。
2. **授權（Authorization，簡稱 AuthZ）**：確認「你能不能做這件事」。系統已經知道你是會員 5012，接著要判斷你能不能看 1002 號訂單、能不能進門市店長後台。如果失敗，HTTP 通常回傳 `403 Forbidden`。

比喻：搭飛機時，過海關看護照是**認證**，確認你就是本人；登機門刷登機證看座位與艙等是**授權**，確認你有沒有資格進頭等艙或搭這班飛機。比喻的極限是：進飛機後通常不會每分鐘重新看一次登機證，但在網站後端，**每一次請求**都要重新檢查認證與授權，因為網站沒有「坐在座位上」這件事，每個 HTTP 請求都是獨立的。

### 三種常見的登入維持方式

總不能每點一個商品就叫顧客重新打一次密碼。通過第一次認證後，系統會用以下幾種方式記住「這個人剛剛驗證過了」：

- **Session＋Cookie**：伺服器在自己的記憶體或資料庫記下一張表（例如「編號 XYZ 代表會員 5012」），只把隨機編號透過 Cookie 交給瀏覽器。好處是伺服器隨時可以把那筆紀錄刪掉，**立刻強制登出**；代價是伺服器要保存與查詢這份狀態。
- **Token（例如 JWT，JSON Web Token）**：伺服器發給用戶端一張「蓋了數位簽章的通行證」，上面直接寫著會員編號與到期時間。收到請求時，伺服器只要驗證簽章對不對，不用查資料庫就知道你是誰。好處是跨網域、多服務或手機 App 很好帶；代價是**在到期前很難單方面作廢**，通常要把效期設得很短，再搭配換發機制。
- **第三方登入（OAuth 2.0 與 OpenID Connect，簡稱 OIDC）**：請外部大型平台幫忙驗證身分。使用者在對方的畫面登入同意後，平台給 Example Retail 一份驗證結果，讓 Example Retail 不用自己保管使用者的密碼，降低密碼外洩的責任。

### 密碼絕對不能明文保存

如果系統選擇自己管理帳號密碼，資料庫裡絕對不能直接存使用者打的密碼本身，而必須經過單向雜湊（hashing）加上隨機鹽值（salt）處理，讓就算資料庫不幸外洩，攻擊者也無法直接反推出原本的密碼。

兩道關卡缺一不可：沒有第一關，誰都能冒充別人；只有第一關沒有第二關，任何已登入的會員都能去偷看或修改別人的資料。

## 取捨

實作登入與身分維持時，三種常見做法的比較：

| 做法 | 適合的情況 | 代價 |
|---|---|---|
| 伺服器端 Session | 一般網站、需要隨時強制登出或立刻收回權限的系統 | 伺服器或共用快取要保存狀態，多台主機時要共用 Session 儲存區 |
| 無狀態 Token（如 JWT） | 手機 App、多個後端服務之間傳遞已驗證身分 | 到期前難以立刻撤銷；通行證內容不能放機敏資料；要另外處理續期 |
| 第三方登入（OIDC／OAuth） | 不想自己保管密碼、希望降低註冊門檻的消費型網站 | 依賴外部登入服務的可用性；需要處理帳號綁定與使用者拒絕授權的情況 |

## 決策題

## 交給 AI 時要注意

- 明確要求每個讀取或修改資料的 API 都要在**後端**驗證資源擁有者（Authorization），不能只靠前端隱藏按鈕。
- 請 AI 說明它選用的是 Session 還是 Token，以及「使用者登出」或「權限被拔除」時要怎麼讓舊憑證立刻失效。
- 檢查密碼與機密金鑰的處理：密碼必須使用安全的雜湊演算法，簽章用的私鑰絕對不能寫死在程式碼裡。

## 重點回顧

- 認證（AuthN）確認「你是誰」，授權（AuthZ）確認「你能做什麼」，兩者順序不同、缺一不可。
- 每個 API 請求都必須在後端做授權檢查，不能因為使用者已經登入就全部放行。
- Session 方便隨時強制登出，Token 方便跨服務傳遞但不易即時撤銷，第三方登入則省去自己保管密碼的風險。
- 系統自己管密碼時，務必經過單向雜湊加鹽保存，絕不存明文。
