## 情境

範圍確認之後，你要把「門市與電商會員合併」、「點數累積與查詢」這些項目寫得更具體：誰會用、怎麼用、出錯時怎麼辦。

IT 主管提醒你：「上一個專案，需求文件只寫了正常流程。上線第一天，門市網路斷線，結帳全部卡住，因為沒人想過平台連不上時該怎麼辦。」

## 觀念

### Use case：描述一個目標的完整互動

Use case（使用案例）描述某個角色（actor）為了達成一個目標，和系統之間的互動。它的重點不只是正常流程，更在於例外流程。

一份 use case 包含：

| 欄位 | 說明 |
|---|---|
| 名稱 | 動詞＋對象，例如「門市結帳時累積點數」 |
| 主要角色 | 發起這個互動的人或系統 |
| 前置條件 | 開始之前必須成立的狀況 |
| 主要流程 | 一切順利時的步驟 |
| 例外流程 | 每一個步驟可能出錯的情況，以及系統怎麼回應 |
| 結果 | 成功時系統的狀態，以及失敗時保證的狀態 |

### 實例：門市結帳時累積點數

- **主要角色**：門市店員（代替會員操作）。
- **前置條件**：會員已註冊；POS 正常運作。
- **主要流程**：
  1. 店員掃描會員條碼。
  2. POS 完成結帳。
  3. POS 把交易送給會員平台。
  4. 平台依規則計算點數並入帳。
  5. 收據印出本次累積點數。
- **例外流程**：
  - 1a. 條碼讀不到：店員輸入會員手機號碼。
  - 3a. 平台無法連線：POS 照常結帳，交易暫存，恢復連線後補送；收據顯示「點數稍後入帳」。
  - 3b. 同一筆交易重複送出：平台以交易編號判斷，只入帳一次。
- **結果**：成功時點數入帳；失敗時結帳不受影響，交易不遺失、不重複入帳。

3a 這一條例外流程，直接回應了「POS 不能停機」的限制。沒有在需求階段寫出來，設計時就可能做成「平台連不上就無法結帳」。

### 使用者故事：小而頻繁的變更

使用者故事（user story）用一句話描述價值：「身為〈角色〉，我想要〈功能〉，以便〈目的〉。」再加上驗收條件。

例如：「身為行銷人員，我想要設定週末點數加倍，以便提高週末的來店率。」驗收條件：「活動期間的交易點數乘以 2；活動開始前和結束後的交易不受影響；活動時間以門市當地時間計算。」

### 什麼時候用哪一種

- **Use case**：流程長、牽涉多個系統、例外情況會造成金額或資料錯誤。
- **使用者故事**：功能小、變化快、可以在一次迭代內完成。
- 兩者可以混用：核心流程用 use case，日常的小變更用使用者故事。

## 取捨

| 寫法 | 適合的情況 | 代價 |
|---|---|---|
| 完整 use case | 核心流程、跨系統、例外會造成金額或資料錯誤 | 撰寫與審閱花時間，小變更也這樣寫會拖慢節奏 |
| 使用者故事＋驗收條件 | 小功能、規則單純、變化快 | 容易漏掉跨系統的例外，需要另外補流程圖 |
| 只列功能清單 | 粗估範圍、排優先順序 | 無法驗收，不能直接拿來實作 |

## 決策題

## 交給 AI 時要注意

- 交給 agent 實作時，例外流程要逐條寫成驗收案例，例如「平台斷線時，POS 交易暫存並在恢復後補送，且只入帳一次」。
- 要求 agent 為每一條例外流程產生測試，並在回報中列出對應關係。
- AI 可以幫你從主流程推想例外情況，但每一條例外的處理方式要由利害關係人確認，不讓 agent 自己決定。
- 使用者故事交給 agent 前，確認驗收條件已經量化，例如時間範圍、時區與計算規則。

## 重點回顧

- Use case 描述角色為了達成目標和系統的完整互動，重點在例外流程。
- 例外流程是把限制（例如 POS 不能停機）變成具體行為的地方。
- 使用者故事適合小而頻繁的變更，一定要附驗收條件。
- 核心流程用 use case，日常小變更用使用者故事，兩者可以混用。
