## 1. 課程定位

- **課程名稱**：SWE Trial。
- **目標**：看懂軟體工程裡常見的技術：每項技術是什麼、解決什麼問題、什麼時候用、和替代方案怎麼選。
- **學習者**：技術基礎不深、還沒決定往哪個方向發展的人。不假設有開發經驗；術語第一次出現就解釋。
- **範圍**：先做兩個領域，Web 與網路基礎（模組 1～3）、資料與後端（模組 4～6）。雲端／DevOps、資安、AI 應用之後再決定要不要加。
- **深度**：概念＋何時用，不寫程式。
- **雲端與產品**：不綁定特定雲端或產品。需要舉例時才提產品名稱，並附官方來源。
- **使用情境**：零碎時間閱讀，手機與電腦都能使用。
- **與其他教材的關係**：本課自成一課，不引用 Learning Atlas 的其他課程。

## 2. 單元格式

每個單元 8～12 分鐘。本文約 1,500～2,500 字，至少一張圖，1～3 題決策題。每個單元固定回答四件事：**它是什麼**、**沒有它會怎樣**、**有哪些替代方案、怎麼選**、**一題情境決策題**。段落固定如下，順序不變：

| 段落 | 內容 | 規則 |
|---|---|---|
| 情境 | Example Retail 遇到的具體問題 | 1～2 段；用生活化的描述帶出「沒有這項技術會怎樣」 |
| 觀念 | 它是什麼、怎麼運作 | 主要篇幅；先講為什麼需要，再講是什麼；用比喻幫助理解，但要說明比喻的極限 |
| 架構圖 | 說明觀念或情境的圖 | 至少一張；每張圖附文字說明 |
| 取捨 | 替代方案比較，說明什麼情況選哪個 | 用表格；每個選項都寫出代價 |
| 決策題 | 情境判斷題 | 1～3 題；3～4 個選項，剛好一個最佳答案，每個選項都有解析 |
| 交給 AI 時要注意 | 這項技術交給 coding agent 實作時，要講清楚什麼、要檢查什麼 | 選填；有寫的話 3～5 點，要具體 |
| 重點回顧 | 本單元要記住的事 | 3～5 點 |
| 延伸閱讀 | 官方文件、規格或經典資料 | 選填；有提到特定產品或雲端服務的單元必填，附查證日期 |

## 3. 寫作規則

- 繁體中文、台灣用語。技術名詞第一次出現時中英並列，例如「網域名稱系統（DNS）」。
- 寫給沒有開發經驗的人：一段只講一個觀念；縮寫第一次出現要展開；不預設讀者看過前面以外的單元。
- 不放程式碼。介面或資料格式可以用簡短的表格或資料範例說明結構（例如一個 HTTP 請求有哪些部分）。
- 產品或雲端服務的功能、限制與價格以官方文件為準，記在單元的 `sources`，附查證日期。沒查證的數字不寫。
- 案例只用 Example Retail。真實企業只能引用公開資料（例如公開的事故報告），要附來源；不使用任何作者雇主、客戶或內部系統的資訊。
- 決策題考判斷，不考背誦：題目給出情境與限制，每個選項都要看起來合理，解析要說明在什麼條件下其他選項才會是對的。
- 內容由 AI 協助撰寫時，單元狀態先標 `draft`，使用者審閱後才改成 `reviewed`（見 `docs/03-system-design.md` 第 4 節）。

## 4. 貫穿案例：Example Retail

虛構企業，整門課共用，用來給每個技術一個具體的使用情境。修改設定時回寫本節。

| 項目 | 設定 |
|---|---|
| 產業 | 連鎖零售（生活用品），全台 120 家門市 |
| 線上服務 | 購物網站、App、會員點數 |
| 規模 | 會員約 80 萬人；週年慶流量約平日 10 倍 |
| 團隊 | 小型 IT 團隊，正在把網站和會員系統重新整理 |
| 常見問題 | 網站在尖峰變慢、門市與網站的資料對不起來、不同系統之間要互相通知 |

各模組使用的情境：

| 模組 | 案例情境 |
|---|---|
| 1 | 顧客在手機上打開購物網站，請求一路送到伺服器 |
| 2 | 購物網站的畫面、登入狀態與載入速度 |
| 3 | App、網站、門市系統與物流商之間怎麼交換資料 |
| 4 | 會員與訂單後端的組成方式 |
| 5 | 會員、商品、訂單與點數的資料怎麼存 |
| 6 | 週年慶的流量尖峰與訂單處理 |
