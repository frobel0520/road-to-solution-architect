## 1. 課程定位

- **目標**：成為 Solution Architect（軟體工程方向），系統分析是基本功。
- **SA 是工程職涯的一個方向**，是工程師在技術職涯上往上走，不是轉職。
- **AI 的角色是交付方式，不是課程主題**：假設程式由 AI coding agent 撰寫，SA 負責需求、架構、交付規格與驗收。每個單元都有「交給 AI 時要注意」段落，模組 9 專門講 AI 輔助交付。
- **雲端平台**：AWS，不對應證照考試。
- **深度**：只講架構層與應用層，不寫程式。
- **使用情境**：零碎時間閱讀，手機與電腦都能使用。

## 2. 單元格式

每個單元 10～15 分鐘。本文約 2,000～3,000 字，至少一張架構圖，1～3 題決策題。段落固定如下，順序不變：

| 段落 | 內容 | 規則 |
|---|---|---|
| 情境 | Example Retail 遇到的具體問題 | 1～2 段，接續前一個單元的案例進度 |
| 觀念 | 核心概念與術語 | 主要篇幅；先講為什麼，再講是什麼 |
| 架構圖 | 說明觀念或情境的圖 | 至少一張；每張圖附文字說明 |
| 取捨 | 選項比較，說明什麼情況選哪個 | 用表格；每個選項都寫出代價 |
| 決策題 | 情境判斷題 | 1～3 題；3～4 個選項，剛好一個最佳答案，每個選項都有解析 |
| 交給 AI 時要注意 | 這個主題交給 coding agent 實作時，規格要寫清楚什麼、要驗收什麼 | 3～5 點，要具體 |
| 重點回顧 | 本單元要記住的事 | 3～5 點 |
| 延伸閱讀 | 官方文件或經典資料 | 選填；有提到 AWS 服務的單元必填，附查證日期 |

## 3. 寫作規則

- 繁體中文、台灣用語。技術名詞第一次出現時中英並列，例如「最終一致（eventual consistency）」。
- 不放程式碼。介面或資料格式可以用簡短的表格或資料範例說明結構。
- AWS 服務的功能、限制與價格以官方文件為準，記在單元的 `sources`，附查證日期。沒查證的數字不寫。
- 案例只用 Example Retail。真實企業只能引用公開資料（例如公開的事故報告），要附來源；不使用任何作者雇主、客戶或內部系統的資訊。
- 決策題考判斷，不考背誦：題目給出情境與限制，每個選項都要看起來合理，解析要說明在什麼條件下其他選項才會是對的。
- 「交給 AI 時要注意」要寫出具體的規格項目或驗收方式，不能只寫「要仔細檢查」。
- 內容由 AI 協助撰寫時，單元狀態先標 `draft`，使用者審閱後才改成 `reviewed`（見 `docs/03-system-design.md` 第 4 節）。

## 4. 貫穿案例：Example Retail

虛構企業，整門課共用。修改設定時回寫本節。

| 項目 | 設定 |
|---|---|
| 產業 | 連鎖零售（生活用品），全台 120 家門市 |
| 通路 | 門市、電商網站、App |
| 會員 | 約 80 萬人；門市與電商的會員資料各自獨立 |
| 既有系統 | 地端 POS（自建，使用十年以上）、套裝 ERP、外包廠商維運的電商平台、用試算表管理的促銷活動 |
| IT 團隊 | 8 人，多數熟悉地端系統；已開始用 AI coding agent 開發 |
| 雲端 | 剛決定導入 AWS，還沒有帳號治理 |
| 主要目標 | 整合會員與訂單，推出全通路會員平台：點數、優惠券、門市取貨 |
| 限制 | 預算有限；必須符合個資法；週年慶流量約平日 10 倍；POS 不能停機 |
| 利害關係人 | 營運長（出資方）、門市營運部、行銷部、IT 主管、資安負責人、外包電商廠商 |

各模組推進的案例進度：

| 模組 | 案例進度 |
|---|---|
| 1 | 為全通路會員平台做需求探索與系統分析 |
| 2 | 畫出平台的 C4 圖，寫下第一批 ADR |
| 3 | 決定平台採用的架構風格，切出 bounded context |
| 4 | 串接 POS、ERP、電商平台與 AI 客服用的 LLM API |
| 5 | 設計會員與點數的資料模型，處理點數一致性 |
| 6 | 設計 AWS 帳號結構與部署架構 |
| 7 | 員工 SSO、會員個資保護、威脅建模 |
| 8 | 週年慶尖峰、SLO、災難復原與成本 |
| 9 | 用 coding agent 交付平台 |
| 10 | PoC → 10 家門市 pilot → 逐步遷移會員資料 |
| 11 | 向營運長提案 |
| 12 | 整合前面所有成果成為完整設計包，並處理一個新加入的需求（門市即時庫存查詢） |
